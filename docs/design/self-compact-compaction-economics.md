# self-compact 压缩经济学：为什么降幅有限、压缩调用为何昂贵

> 基于一次真实会话（neonspark，2026-11-12 09:35–09:56，1M 窗口模型）的实测数据分析。
> 本文记录现状与推论；已执行的部分是水位线调整，其余列为待定项。

## 1. 结论摘要

1. 压缩只释放了 **40%**，因为剩余上下文里有三分之二不是「可压缩的对话历史」：固定系统提示/工具 schema、Pi 按 `keepRecentTokens` 保留的近端尾部、压缩摘要本身、以及 handoff 卡片。
2. 压缩调用本身花 **87,968 tokens**，其中 input 74,939 **完全没有命中缓存**（输入等效成本约 140k），且压缩会把整段缓存前缀作废（再 +139k）。每次压缩的一次性成本约 **279k 输入等效 token**。
3. 在 1M 窗口 21% 处压缩（仍有 790k 余量）时，每轮只省约 8.2k，**回本需要约 34 轮**。压得越早越亏：70% 触发时回本约 13 轮，90% 时约 12 轮。
4. handoff 卡片与压缩摘要**文本重复度很低**（12 字符 shingle 重合 8.7%），主题互补；但卡片有 51% 的篇幅是模型自行追加的内容，与摘要同质，属于可删膨胀。

## 2. 实测数据

### 2.1 压缩前后

| 时点 | prompt tokens | 占 1M 窗口 |
|---|---|---|
| 压缩前最后一次请求 | 203,372 | 20.3% |
| Pi 记录的 `tokensBefore`（估算） | 211,094 | 21.1% |
| 压缩后第一次请求 | 121,209 | 12.1% |
| TUI 显示（含 output 4,435） | 125,644 | 12.6% |

实际移除 **82,163 tokens（−40.4%）**。

### 2.2 压缩后 121,209 的构成

| 组成 | tokens | 占比 | 依据 |
|---|---|---|---|
| 保留近端尾部（39 条消息，79,009 字符） | ~35–50k | 30–40% | `keepRecentTokens: 20000` |
| 系统提示 + 工具 schema（固定底座） | ≥39k | ≥32% | 本会话首个请求实测 39,067，当时内容仅 435 tokens |
| 压缩摘要（17,091 字符） | 13,029 | 11% | 摘要调用的 `output=13029` |
| handoff 卡片（11,455 字符） | ~8,700 | 7% | 实测字符/token ≈ 1.31 |
| tokenize 差异余量（thinking 等） | 其余 | — | 估算器与真实分词差异 |

### 2.3 关键机制：Pi 的估算器是 `chars / 4`

`compaction.js:201-246` 的 `estimateTokens()` 对所有角色统一 `Math.ceil(chars / 4)`。中文实际约 **1.3 字符/token**，即低估约 3 倍。两个直接后果：

- **保留尾部超标**：79,009 ÷ 4 = 19,752 ≈ 20,000，Pi 认为严格遵守了 `keepRecentTokens`，真实占用却是 35–50k。
- **摘要低估**：17,091 ÷ 4 = 4,273，实测 13,029（来自摘要调用自身 usage）。

因此在中文密集会话里，「20k 保留窗口」的真实代价是配额的 2–3 倍。

## 3. 压缩调用的成本结构

### 3.1 87,968 从哪来

```
input        74,939   ← 被丢弃的 102 条消息（350,662 字符）序列化文本
output       13,029   ← 摘要本身
reasoning     3,112
cacheRead         0   ← 无缓存命中
cacheWrite        0
```

- **input 只算被丢弃的部分**，不是整个 211k。摘要成本随「丢弃量」增长，而非随总上下文增长。
- **缓存命中率为 0**：Pi 用独立的 `SUMMARIZATION_SYSTEM_PROMPT` + 单条 user 消息包裹 `<conversation>`（`compaction.js:499-530`）。provider 缓存按前缀匹配，system prompt 一换即全 miss，74,939 全价。

### 3.2 换算为输入等效 token

计价系数取 Anthropic 口径：input 1× / cacheWrite 1.25× / cacheRead 0.1× / output 5×。

| 项目 | 等效 tokens |
|---|---|
| 摘要调用 74,939×1 + 13,029×5 | 140,000 |
| 压缩后首轮缓存重写 114,392×1.25（对比平时增量写 ~3k×1.25） | +139,000 |
| **一次性成本** | **≈ 279,000** |
| 每轮节省 82,163×0.1 | **8,200** |

**回本 ≈ 34 轮。**

### 3.3 在不同触发水位下的回本

| 触发水位 | 丢弃量 | 每轮省 | 一次性成本 | 回本 |
|---|---|---|---|---|
| 21% | 82k | 8.2k | 279k | 34 轮 |
| 70% | ~600k | 60k | ~774k | 13 轮 |
| 90%（hard） | ~800k | 80k | ~980k | 12 轮 |

压缩的能源效率上限约 10%（一次付 1，之后每轮省 0.1）。**压得越早，单位收益越差。**

### 3.4 缓存机制决定结论

| provider | 缓存类型 | 写入罚金 | 压缩重写代价 | 回本 |
|---|---|---|---|---|
| Anthropic 系 | 显式（写 1.25×，读 0.1×，5 分钟 TTL） | 有 | 121k×1.25 ≈ 151k | ~34 轮 |
| DeepSeek / Gemini | 隐式（命中即打折，无写费） | 无 | ≈ 0 | 2–4 轮 |
| OpenAI | 自动前缀缓存（约 0.5×） | 无 | 121k×0.5 ≈ 60k | ~10 轮 |

同一套水位在 DeepSeek/Gemini 上几乎无痛，在 Anthropic 系上代价最高。该会话主模型是 `teamorouter-claude`，恰属最不划算的一类。

### 3.5 缓解因素

第二次及以后的压缩走 `UPDATE_SUMMARIZATION_PROMPT`，携带 `<previous-summary>`，只摘要新增消息（`compaction.js:517-529`）。重复压缩的 input 会小于 87k，但 output 仍约 13k（5× 计费），且每次都重写缓存前缀。在 Anthropic 系上频繁触发仍为净亏。

## 4. 已执行：水位线调整

`.pi/managed/self-compact.json`：

```json
{ "softAt": "70%", "at": "75%", "buffer": "5%", "hardCeilingPercent": 90 }
```

解析结果（窗口 1,000,000）：notice 700,000 / recommend 750,000 / forced 800,000（`75%+5%`），硬上限 900,000。

| 档位 | 之前 | 现在 | 行为 |
|---|---|---|---|
| notice（`softAt`） | 10% | 70% | 状态栏提示 + guidance 文本 |
| recommend（`at`） | 20% | 75% | 触发一次 Jev 边界判断，给出建议 |
| forced（`at + buffer`） | 30% | 80% | 加锁、拦截非 `self_compact` 工具 |
| 硬上限 | 90% | 90% | 不超过该比例 |

理由：在 1M 窗口保持 10/20/30 会让压缩发生在还有 790k 余量的位置，回本要 34 轮；推到 70% 触发、80% 执行，回本降到 13 轮，同时保留「撞墙前必被提醒」的安全性。三档语义未变，中间档仍承担 Jev 边界判断。

## 5. handoff 卡片与压缩摘要的重复度

### 5.1 实测重合很低

| 指标 | 结果 |
|---|---|
| 12 字符 shingle 重合 | 卡片 9,581 个中 837 个出现在摘要里 = **8.7%** |
| 文件路径 | 摘要 86 个 / 卡片 57 个，共享 11 个 |
| 主题分工 | 摘要偏「任务与约束」（`openspec` ×33）；卡片偏「下一步与代码细节」（`harness-router` ×17，`T3/T5/T6` ×15，`pytest` ×6） |

两者语义互补，分层设计成立：摘要记录「上下文里发生过什么」，卡片承载「恢复后要接着做什么」。

### 5.2 卡片自身有 51% 是膨胀

```
11,456 字符
├─ 六字段本体        5,563  (49%)  Goal 229 / Done 2,264 / InProgress 91
│                                  Decisions 1,007 / Refs 1,535 / NextAction 278
└─ 模型自行追加       5,893  (51%)
   · 模块与 API（扁平 import…）  2,527
   · 待做 T3 详细要求            1,377
   · 后续 T5/T6 要求               720
   · 已知环境坑                    708
   · 现状 / 测试现状 / G2 未决     653
```

三块与摘要同质：

1. `Preserved References`（1,535）与摘要的 `readFiles` / `modifiedFiles` 清单重复（摘要尾部即完整路径表）。
2. `模块与 API`（2,527）是可随时 `read` 回来的代码库事实。
3. `Done`（2,264）与摘要的「已完成什么」重复。

卡片约 8,700 tokens，其中约 4,500 可删。

## 6. 待定项（本次未执行）

| 项 | 预期收益 | 风险 |
|---|---|---|
| 卡片总长上限 6,000 字符，`note` 上限 2,000 | 每轮省 ~4,500 tokens（1M 窗口 0.45 点），并降低压缩后再膨胀速度 | 交班信息变薄 |
| `Preserved References` 上限 8 条 | 每轮省 ~1,100 tokens | 需 `read` 回溯引用 |
| 摘要 `customInstructions` 要求省略代码细节 | 摘要 17k→10k 字符，input/output 双向省 | 摘要密度下降 |
| 按窗口大小分档水位（大窗口自动上移） | 免去手工调参 | 增加配置复杂度 |

前两项改动扩展代码（`handoff.ts` / `index.ts` 的 schema 与 `note` 处理），第三项改 `customInstructions`，均需单测与真机复测。

## 7. 相关 spec 已同步

`openspec/specs/self-compact/spec.md` 原先在 Purpose 段与两个 Requirement 里硬编码了 `softAt: "10%"` / `at: "20%"` / `buffer: "10%"` 及对应 token 数，与本配置落地后的实际取值直接矛盾。该问题已通过 OpenSpec change `2026-11-12-self-compact-watermark-config-agnostic` 修正：spec 现在只约束「如何读取、如何解析、如何夹取、如何校验」，所有具体数值归配置所有。
